# Release Pipeline and Hosted Demo

**Our** infrastructure, not the customer's. For customer-side deployment see [customer_deployment.md](customer_deployment.md).
**Decisions:** ADR-0001 (single binary), ADR-0014 (offline licence, same binary for both offerings).

---

## 1. What this covers

Two things we run on GCP:

1. **The release pipeline** — how the binary is built, signed and published.
2. **The hosted demo** — a public instance a prospect can click through, running seeded fixture data.

Deliberately excluded: a SaaS control plane, per-tenant infrastructure, a billing system. The hosted offering, when it exists, is **this binary run by us for one customer** — a licence issued to ourselves, not a different product. That is the constraint that keeps the self-managed build from becoming the untested one.

## 2. Release pipeline

```
git tag v1.0.0
   └─> GitHub Actions
         ├─ go vet, staticcheck
         ├─ go test ./...                     unit + fixture corpus
         ├─ integration tests                 against the test lab
         ├─ goreleaser
         │    ├─ linux/amd64  linux/arm64
         │    ├─ darwin/amd64 darwin/arm64
         │    ├─ windows/amd64
         │    └─ CGO_ENABLED=0, -trimpath, ldflags with version + commit
         ├─ cosign sign-blob per artefact
         ├─ syft → SBOM (SPDX) per artefact
         └─ publish
              ├─ GitHub Releases              checksums, signatures, SBOMs
              └─ GCS bucket behind Cloud CDN   download.nagipath.dev
```

### 2.1 Choices worth stating

**Five platforms, one codebase.** `CGO_ENABLED=0` and pure-Go SQLite are what make cross-compilation trivial. Choosing `mattn/go-sqlite3` would have made this a matrix of cross-compilers and would have cost the static-binary property that the whole distribution story depends on — which is why that decision is an ADR rather than a preference.

**Signatures and SBOMs from day one, not when a customer asks.** The buyer is an enterprise security review. A signed artefact with an SBOM turns a procurement objection into a link, and adding it later means the first two customers were shipped unsigned binaries. It costs two pipeline steps.

**`-trimpath`** so build paths do not leak our filesystem layout into the binary.

**Version is compiled in**, not read from a file. `nagipath version` reports the tag, commit and build time, which is the first thing asked in every support conversation.

### 2.2 Release checklist

Enforced in the pipeline, not by memory:

- Migrations are forward-only and additive; no migration file is ever edited after release.
- `parser_version` is bumped when parsing behaviour changes, so derived data is recomputed rather than displayed stale.
- `CHANGELOG.md` names schema changes and any parser change explicitly, because those are the two that affect customer data.
- The upgrade note says take a backup first, since rollback is a restore ([customer_deployment.md §7](customer_deployment.md)).

## 3. Hosted demo

`demo.nagipath.dev` — one Cloud Run service, the release binary, `NAGIPATH_DEMO_MODE=1`, a seeded database baked into the image.

```
Cloud Run  (min 0, max 2, 512 MB)
   image: gcr.io/nagipath/nagipath:v1.0.0-demo
   env:   NAGIPATH_DEMO_MODE=1
          NAGIPATH_DB=/data/demo.db      (read-mostly, seeded at build)
   ↑
Cloud Load Balancer + managed TLS
```

### 3.1 Why the real binary and not a marketing mock

A separate mock would drift from the product within one release, and every screenshot in it would eventually be a lie. Running the shipped binary means the demo is always accurate, costs nothing to maintain, and doubles as a smoke test of the release artefact — if the demo starts, the binary starts.

### 3.2 Demo mode behaviour

| Behaviour | Reason |
|---|---|
| Permanent banner | Nobody should mistake it for their own install. |
| **Probes refused outright** | The demo host must never send traffic anywhere. This is the guardrail that makes a public demo safe at all. |
| Credential and User management disabled | No credential form on a public URL, even a fake one. |
| Collection disabled | There are no real Nodes; a spinner going nowhere is worse than an honest refusal. |
| Everything else fully functional | Trace, Rule Lookup, Drift, Certificates, Search — all real code over seeded data. |
| Database resets on cold start | Any state a visitor creates is discarded. Ephemeral by construction, not by cleanup job. |

`min instances = 0` means the first visitor waits a few seconds for a cold start. Accepted: this is a demo, not a service, and paying for a warm instance around the clock to save four seconds is the wrong trade.

### 3.3 The seeded fleet

Generated by `nagipath demo seed` from checked-in fixtures — the same fixtures the test corpus uses, so the demo cannot show a topology the parser cannot actually handle.

It has to be honest as well as impressive, so it deliberately contains problems:

- 12 Nodes, 15 Instances across NGINX, Apache and HAProxy.
- A four-hop cross-vendor Trace with a path rewrite — the core demo.
- A Trace ending in an External Hop, because real fleets do.
- **A shadowed `add_header` with a Probe result showing the header absent** — the strongest single artefact the product produces.
- A Cluster with three diverging members and suggested ignore rules, so the noise-management story is visible rather than described.
- A certificate expiring in 24 days with 12 Bindings across 6 Nodes.
- A certificate whose SANs do not cover the Site serving it.
- An Instance whose NGINX `log_format` blocks verification, showing the honest limit.
- Two unmodelled directives, shown verbatim as unmodelled.

The last three matter as much as the first. A demo with no gaps invites the suspicion that the gaps are being hidden, and the honest-limit screens are a large part of why this product earns trust.

## 4. Other infrastructure

| Component | Choice | Note |
|---|---|---|
| Marketing site | Static, GCS + Cloud CDN | No CMS. |
| Documentation | Static generated from `docs/` | Single source with the repository. |
| Downloads | GCS + Cloud CDN | Signatures and SBOMs alongside. |
| Licence issuance | Offline CLI, key in Secret Manager | **No licence server.** Sign a token, send the file. Nothing to run, nothing to have an outage. |
| Support | Email plus a GitHub issue tracker | |
| Our own hosted customers | One Cloud Run or GCE instance per customer, our own licence, standard backups | The same binary. No multi-tenant code path exists. |

The absent licence server is worth calling out. A licence server is a service to operate, a dependency for customers, and an outage that breaks other people's installations. Signing tokens offline with a key in Secret Manager gives the same commercial control with nothing to run.

## 5. What we deliberately do not build

| Not built | Why |
|---|---|
| Multi-tenant SaaS control plane | The hosted offering is one instance per customer. Multi-tenancy in the data model would be a large, permanent, load-bearing complexity for revenue that does not exist yet. |
| Auto-update in the binary | Requires outbound network from the customer's install, which contradicts the air-gapped promise and adds a supply-chain surface. Operators upgrade binaries; they know how. |
| Telemetry or usage reporting | Would fail the security review that everything else in this design is built to pass. |
| Licence server | See above. |
| Container as the primary distribution | Provided as a convenience, but the binary is primary. A container implies a runtime dependency the product does not have. |
| Helm chart, operator, Terraform module | The product is one process and one file. Packaging it as a distributed system would misrepresent it. |

## 6. Acceptance criteria

| # | Criterion |
|---|---|
| 1 | A tag produces signed artefacts for five platform targets with checksums and SBOMs. |
| 2 | All artefacts are `CGO_ENABLED=0` static builds with `-trimpath`. |
| 3 | `nagipath version` reports tag, commit and build time compiled in. |
| 4 | The pipeline fails on vet, staticcheck, unit tests, fixture corpus or integration tests. |
| 5 | The pipeline fails if a previously released migration file has been modified. |
| 6 | The pipeline fails if parsing behaviour changed without a `parser_version` bump. |
| 7 | The demo runs the release binary, not a fork or a mock. |
| 8 | Demo mode refuses Probes, Credential management, User management and Collection. |
| 9 | Demo state resets on cold start. |
| 10 | The seeded fleet is generated from the same fixtures as the test corpus. |
| 11 | The seeded fleet includes a shadowed header with Probe disproof, an External Hop, a verification blocker and unmodelled directives. |
| 12 | Licences are signed by an offline CLI; no licence server exists. |
| 13 | Our hosted customers run the same binary with no SaaS-only code path. |
| 14 | The binary makes no auto-update or telemetry call. |
